# Bug Fixing and Resolution Implementation Plan

## Executive Summary
This plan provides a systematic approach to implement fixes for GitHub issues created during the bug migration process. It follows Test-Driven Development (TDD) methodology, ensuring each fix is thoroughly tested before implementation. The system leverages Herdr for parallel processing, Playwright for end-to-end testing, and automated PR creation for code review.

Key features:
- **TDD Methodology**: Write tests first, then implement fixes
- **Automated Testing**: Unit, integration, and E2E testing with Playwright
- **Human Review Process**: QA department review with "ready" flagging
- **Automated Documentation**: Test results posted as GitHub issue comments
- **PR Automation**: Automatic pull request creation to original branches

## Overview
This plan implements fixes for GitHub issues generated by the bug migration system. It uses the resolution plans created during migration, applies TDD methodology, and ensures comprehensive testing before code is committed. Human developers review issues and mark them as "ready for agent" for implementation. After implementation, developers review PRs, merge, and deploy. Once deployed, QA personnel manually review fixes on QA servers using provided validation instructions.

## Prerequisites
- Ubuntu in WSL environment
- Git CLI tools installed
- GitHub CLI (gh) installed
- Herdr terminal workspace manager
- Playwright testing framework
- Node.js and npm for testing
- Appropriate permissions for GitHub repository

## Phase 1: System Setup and Issue Identification

### 1.1 Environment Preparation
```bash
# Install required tools
sudo apt update
sudo apt install -y git curl jq nodejs npm

# Install GitHub CLI
curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg | sudo dd of=/usr/share/keyrings/githubcli-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" | sudo tee /etc/apt/sources.list.d/github-cli.list > /dev/null
sudo apt update
sudo apt install gh

# Install Playwright
npm init playwright@latest

# Authenticate with GitHub
gh auth login

# Set up working directory
mkdir -p ~/bug-fixing-project
cd ~/bug-fixing-project
```

### 1.2 Identify Issues Ready for Fixing
```bash
# Create bash script to find issues ready for fixing
cat > get-ready-issues.sh << 'EOF'
#!/bin/bash

STATUS_LABEL=${1:-"ready"}

# Get GitHub issues with the specified status label
issues=$(gh issue list --label "$STATUS_LABEL" --state open --json number,title,body)

# Save to JSON file
echo "$issues" > ready-issues.json

issue_count=$(echo "$issues" | jq length)
echo "Found $issue_count issues ready for fixing"
EOF

chmod +x get-ready-issues.sh
```

```bash

#!/bin/bash

ISSUES_FILE=${1:-"ready-issues.json"}

# Test development script for issue $issue_number
cd "../$worktree_path"

# Checkout the fix branch created during migration
git fetch origin
git checkout -b "fix-issue-$issue_number" "origin/fix/$issue_number-main"

# Parse the resolution plan from the issue body
# Extract files to modify and test requirements

# 1. Create unit tests to reproduce the issue (failing tests first)
# 2. Create integration tests
# 3. Set up Playwright E2E tests

# Example unit test creation (using your project's testing framework)

echo "Test development completed for issue $issue_number"
TEST_SCRIPT

    # Execute in background using Herdr

chmod +x start-parallel-testing.sh
```

## Phase 5: Pull Request Creation and Automation

### 5.1 Specialized Skill: Automated PR Creation
```bash
# Create PR creation skill
cat > new-pull-request.sh << 'EOF'
#!/bin/bash

ISSUE_NUMBER=$1
SOURCE_BRANCH=${2:-"fix-issue-$ISSUE_NUMBER"}
TARGET_BRANCH=${3:-"main"}

# Get issue title for PR title
issue_title=$(gh issue view "$ISSUE_NUMBER" --json title | jq -r '.title')

# Create PR title and body
pr_title="Fix: $issue_title"
pr_body="This PR implements the fix for issue #$ISSUE_NUMBER.

## Changes Made
- [ ] Fix description 1
- [ ] Fix description 2

## Tests Performed
- ✅ Unit tests
- ✅ Integration tests
- ✅ E2E tests (Playwright)

## Test Results
See comments on issue #$ISSUE_NUMBER for detailed test results.

## Related Issues
Closes #$ISSUE_NUMBER"

# Create pull request
gh pr create --title "$pr_title" --body "$pr_body" --base "$TARGET_BRANCH" --head "$SOURCE_BRANCH"

# Add labels
gh pr edit --add-label "bugfix,automated"
EOF

chmod +x new-pull-request.sh
```

### 5.2 Parallel PR Creation with Herdr
```bash
# Create parallel PR creation script
cat > create-parallel-prs.sh << 'EOF'
#!/bin/bash

ISSUES_FILE=${1:-"ready-issues.json"}

# Load issue data
issues=$(jq -c '.[]' "$ISSUES_FILE")

# Create PRs in parallel using Herdr
echo "$issues" | while read -r issue; do
    issue_number=$(echo "$issue" | jq -r '.number')
    
    cat > "create-pr-$issue_number.sh" << PR_SCRIPT
#!/bin/bash
# Create PR for issue $issue_number
./new-pull-request.sh "$issue_number" "fix-issue-$issue_number" "main"
PR_SCRIPT
    
    # Save script
    chmod +x "create-pr-$issue_number.sh"
    
    # Execute in background using Herdr
    herdr agent start "pr-$issue_number" -- bash "create-pr-$issue_number.sh"
done

# Wait for all PR creations to complete
herdr agent list | grep "pr-" | while read -r agent; do
    herdr agent wait "$agent"
done
EOF

chmod +x create-parallel-prs.sh
```

### QA Reporting Process

#### For Approved Fixes:
1. Add "qa-approved" label to the GitHub issue
2. Comment on the issue: "✅ QA validated - Ready for production deployment"
3. Notify development team via Slack: "@dev-team QA approved for issue #[number]"

#### For Issues Requiring Changes:
1. Remove "qa-approved" label if present
2. Add "qa-feedback" label
3. Comment on the issue with detailed feedback:
   ```
   ❌ QA validation failed
   
   Issues found:
   1. [Specific issue description]
   2. [Steps to reproduce]
   3. [Expected vs actual behavior]
   
   Screenshots: [Attach if applicable]
   ```
4. Notify development team via Slack: "@dev-team QA feedback for issue #[number]"

#### For Critical Issues:
1. Immediately add "critical-bug" label
2. Comment with urgent priority flag
3. Notify team via Slack with "@here" or "@channel"
4. Escalate to project manager if needed
